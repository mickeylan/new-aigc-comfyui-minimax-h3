## 3. T01：Chrome 上限视频播放（最优先）

**历史问题：** 2880 帧视频导出与素材入库成功，Chrome 内嵌播放报解码错误。根因尚未定位，不能直接认定显卡弱或文件坏。

1. 先不重渲染，分别用新机 Chrome 打开旧对照视频和旧上限视频，手动点击播放（避免把自动播放权限 `NotAllowedError` 当解码错误）。
2. 上限视频从头连续播到结束，再拖动到约 60 秒、110 秒各播放一段；记录有无黑屏、卡死、错帧、提前结束和错误。
3. 在产品「逐镜视频导出与生成交接」面板新导出上限视频后，再验**面板内嵌播放**；外部文件能播不等于面板内能播。
4. 记录 Chrome 完整版本、`chrome://gpu` 的渲染器/硬件加速状态、驱动版本；保存控制台和 `chrome://media-internals` 对应媒体错误（分享前去除私有路径/地址）。
5. 若仍失败，保留原文件与清单；可在独立 Chrome profile 中切换一次硬件加速作对照，重启后复测并分别记录。不要无限重试或用较低 FPS 的成功替代 24fps 上限结论。

可选：装有 FFmpeg 时，对下载文件进行独立检查（把路径换成实际视频）：

```powershell
ffprobe -v error -select_streams v:0 -count_frames -show_entries stream=codec_name,width,height,r_frame_rate,nb_read_frames:format=duration,size -of json "studio-shot-previs.webm"
ffmpeg -v error -xerror -i "studio-shot-previs.webm" -map 0:v:0 -f null -
```

**预期：** 上限视频为 1280×720、24fps、2880 帧、约 120 秒；面板内从头到尾可播、拖动后恢复播放，无媒体解码错误。保留命令退出码，FFmpeg 成功与浏览器成功分别填写。

补充证据：整理本文时发现现存 `.rscode/software-video-decode-result.json` 记录两段前 1 秒 VP9 码流样本，普通样本 12 入/12 出、上限样本 24 入/24 出、error=null。该诊断使用 `prefer-software`，**不能证明实际一定采用软件解码，也不能证明完整 WebM 封装、全片或内嵌播放器通过**；历史命令超时仍单独保留，不据此归因。

## 4. T02：1577 实例大场景交互

1. 用「载入场景」打开 `studio-recipe-scale.json`，确认载入 **1577 个实例**，不是用零件数或 draw call 数代替对象数；不要靠隐藏大部分对象降低负载。
2. 记录窗口尺寸、画布像素尺寸、系统缩放/DPR、浏览器缩放和天气。可做一组尽量接近原机的条件：viewport 1582×904、DPR=1、canvas 1568×882；不能匹配则明确写差异。
3. 页面保持前台，预热约 10 秒；分别观察/测量 30 秒静置、30 秒旋转/平移/缩放。记录卡顿、长帧、黑屏、WebGL context lost；有开发者工具时保存 Performance 记录，并注明录制本身的开销。
4. 连续执行：选择对象→移动/旋转→撤销→隐藏/显示→保存场景→重新载入。检查操作是否可响应、修改是否保存、撤销是否正确。
5. 如需多轮，仅在没有无响应/资源耗尽时继续；保留慢窗口，不删异常样本。页面无响应后先保留证据，停止施压。

**历史基线：** GTX 960，15 个窗口共 30375.2ms，RAF 加权约 12.7077 次/秒，窗口 7.49–13.65，p95 83.5–563.4ms；观察峰值 JS 堆 363062948 字节。后续纯网格跳过空 Spark 遍历的修改有功能测试，但**没有同条件优化前后加速证据**。

**判定：** 分别填写“操作正确性”和“流畅性”。记录实测帧率/长帧与主观卡顿，不把 RAF 次数当 GPU 完成帧率；目前未约定硬性 FPS 门槛，不把“能显示出来”直接记作性能通过，也不从不同机器数字计算代码优化倍数。

## 5. T03：跨设备保存恢复与导出稳定性

1. 在新机载入同一测试档，检查对象、镜头表、机位、角色动作、环境/地形；保存到本地，再载入核对。使用后端存档时只存新机的测试项目。
2. 对 `pressure64-archive.json` 导出参考包，核对 **64 镜 × 3 张 PNG + manifest.json = 193 条目**；PNG 尺寸按该次视口与清单核对，不能硬套视频的 1280×720。
3. 先做 64 秒/12fps 视频（预期 768 帧），再做 120 秒/24fps 上限视频（预期 2880 帧）。分别记导出墙钟耗时、字节数、播放结果和峰值资源。原机耗时约 70.3 秒/232.6 秒，只作历史记录，不是新机超时阈值。
4. 核对视频与追溯清单对应：artifactId、帧数/FPS、时间范围、场景来源、输出模式一致；导出后场景/人物/机位还原。
5. 可选复查取消与超帧限制：导出中取消不得留下半成品或自动入库；121 秒×24fps=2904 帧应明确拒绝，不得截断。**这两项原机已通过，只是新机回归，不属于原先失败项。**
6. 浏览器接近 256MiB 的体积边界压力尚未实测；无需为填“通过”刻意制造超大场景。没做就填未验收。现有 CPU 编码/封装预算测试不能冒充真实浏览器极限实测。
7. 四项修复回归（不是硬件性能通过）：同角色连续两镜沿坡行走，切镜不应掉回第一镜起点高度；载入未启用环境的夜晚预设旧档，灯光/背景应保留夜晚；五画幅视频导出中改变窗口大小，视频及清单保持固定目标尺寸，结束/取消后视口按新容器恢复；素材超过100条时仍能选到本项目与共享视频、不列其他项目视频。

## 6. T04：内存与显存

- 在 T02/T03 的空载、载入后、导出中、结束后分别记录 JS 堆/浏览器内存；能观察时记录峰值与采样间隔。
- GPU 显存可用系统任务管理器按浏览器进程观察，或 NVIDIA 工具观察。注明是进程值还是整卡值、专用还是共享内存、是否还有 ComfyUI/其他程序占用。
- 整卡显存不能直接归因于本网页；稀疏采样的最大值只能叫“观察到的峰值”，不是精确瞬时峰值。
- 工具不提供时写 **不可得**，不要把 JS 堆大小换算成 GPU 显存。

## 7. T05：真实生成交接（有 ComfyUI 才做）

**原机状态继续是 SKIPPED，不是通过，也不要求今晚必须做。以下是你在可用测试环境自行执行的步骤，本轮没有启动实例或提交真实生成。**

1. 使用独立测试项目，确认目标实例、专用 3D 参考视频模板和模型/节点就绪；不能以模拟模式成功代替真实生成。
2. 先用短测试视频，不拿 120 秒上限视频假设模型一定支持。选择时长、分辨率等须符合目标实例实测能力。
3. 在面板人工确认入库，记录素材 ID/名称、清单 artifactId。若提示后端未确认来源，先核对版本和已有素材，不重复上传。
4. 项目 → Scene → 编辑视频提示词 →「3D结构参考视频」选择该素材，核对并保存。刷新确认关联仍在，既有首尾帧没有被覆盖；保存本身不能自动创建生成任务。
5. 核对后由你显式提交一次测试生成。记录任务 ID、模板、目标实例和节点实际收到的参考视频；失败或结果未知时先查任务/历史，**不盲目重交**。
6. 核对任务成功状态、输出文件可播放以及生成快照中的素材 ID/派生清单与入库记录一致。明确区分“输入节点收到视频”和“输出视觉效果符合预期”，来源清单不是模型确实利用了视频的证明。
7. 专用模板不可用时必须明确拒绝，不能静默回退并丢掉参考视频。此错误分支离线已测，可在隔离测试环境回归，不修改正式模板。

# 长篇小说改编漫剧 · 详细实施方案

> 日期：2026-09-14
> 适用项目：ComfyStudio AI 漫剧工作台
> 目标：把当前“故事梗概一次生成全剧”的流程升级为可处理数十万字长篇小说、可追溯到原文章节、可逐级审核和断点恢复的改编流水线。

---

## 1. 背景与问题

当前 `Project.Synopsis` 同时承担故事梗概和创作源文本，`GeneratePlan` 会把它一次性提交给文本模型。这对梗概和短篇有效，但不适合长篇小说：

1. 全文容易超过模型上下文，后半部分被截断或弱化。
2. 一次摘要会丢失人物关系、伏笔、时间线和关键物件。
3. 一次规划几十集时，后半段容易重复、空泛或偏离原著。
4. 当前角色档案是单一静态版本，无法表达身份、服装、关系随剧情阶段变化。
5. 分集没有明确记录“改编自哪些章节、必须保留哪些事件”。
6. 小说解析、摘要失败后缺少章节级重试和断点续跑。

因此长篇改编必须采用“分章存储、分层理解、按集检索”的方式，不能把全文反复塞给 LLM。

---

## 2. 产品目标与边界

### 2.1 目标

- 支持 TXT、Markdown 小说导入，首版覆盖 UTF-8/UTF-8 BOM。
- 自动识别卷、章；识别失败时提供人工拆章和重新编号。
- 每章独立生成结构化摘要、角色、事件、地点、道具、伏笔与状态变化。
- 按 5~10 章形成剧情单元，再汇总为全书故事圣经。
- 生成“原文章节 → 漫剧分集”的明确映射。
- 每集默认约 180 秒、25 镜头，并能追溯引用的原文片段。
- 前后集生成时传入连续性状态，避免人物位置、物品、伤势、关系跳变。
- 所有 LLM 阶段通过现有 Skill 管理框架装配，并记录版本审计。
- 所有长任务可暂停、失败重试、从断点恢复，不因单章失败重跑全书。

### 2.2 首版不做

- 不引入向量数据库；先使用 SQLite FTS5（可用时）或关键词/章节映射检索。
- 不做 EPUB/PDF OCR；第二阶段再增加 DOCX/EPUB。
- 不自动规避版权问题；只处理用户有权使用的内容，并在导入页提示权利确认。
- 不直接让模型自动生产整本小说全部视频；先审核故事圣经和分集映射。
- 不训练角色 LoRA；继续使用 Krea2 角色资产和 MiniMax H3 工作流。

---

## 3. 总体流程

```text
导入小说文件
  ↓
编码检测、清洗、章节切分
  ↓
章节清单人工确认
  ↓
逐章结构化分析（可并行、可重试）
  ↓
剧情单元归并（每 5~10 章）
  ↓
全书故事圣经 + 时间线 + 关系图 + 伏笔台账
  ↓
用户选择改编范围与策略
  ↓
生成分集映射（约 180 秒/集）
  ↓
用户审核、调整章节范围和必保事件
  ↓
按集检索原文 + 前后集状态 → 生成剧本
  ↓
连续性审查 → 分镜 → Krea2/H3 生产链路
```

核心原则：生成某一集时仅提供：

1. 全书故事圣经的精简稳定部分；
2. 当前集映射的原文章节和关键片段；
3. 上一集结束状态和下一集目标；
4. 当前角色阶段档案；
5. 当前集必须保留/允许改写/禁止改写的事件。

## 4. 数据模型

### 4.1 `NovelSource` 小说源

```go
type NovelSource struct {
    ID             uint
    ProjectID      uint   // unique
    Title          string
    OriginalName   string
    StoragePath    string // 原文件路径，不直接塞数据库
    Encoding       string
    ContentHash    string // SHA-256，防重复导入
    WordCount      int
    ChapterCount   int
    ImportStatus   string // uploaded/parsing/ready/failed
    AnalysisStatus string // pending/running/partial/ready/failed
    Error          string
    CreatedAt      time.Time
    UpdatedAt      time.Time
}
```

完整原文建议保存到项目数据目录：

```text
input/<project_id>/novel/source.txt
```

数据库只保存路径、哈希和统计，避免 SQLite 单行存放数十万字。

### 4.2 `NovelChapter` 章节

```go
type NovelChapter struct {
    ID             uint
    NovelID        uint
    ChapterNo      int
    VolumeNo       int
    Title          string
    Content        string // 首版可存 SQLite TEXT；超大时改文件分片
    ContentHash    string
    WordCount      int
    StartOffset    int64
    EndOffset      int64
    Summary        string
    AnalysisJSON   string
    AnalysisStatus string // pending/running/ready/failed/stale
    AnalysisVersion int
    Error          string
}
```

唯一索引：`(novel_id, chapter_no)`。

`AnalysisJSON` 结构：

```json
{
  "summary": "本章摘要",
  "events": [{"id":"E12","event":"事件","cause":"原因","result":"结果","importance":5}],
  "characters": [{"name":"角色","state_before":"","state_after":"","relationship_changes":[]}],
  "locations": [],
  "props": [],
  "clues_opened": [],
  "clues_resolved": [],
  "timeline": [{"relative_time":"三天后","event":"..."}],
  "must_keep_quotes": []
}
```

### 4.3 `StoryArc` 剧情单元

```go
type StoryArc struct {
    ID           uint
    ProjectID    uint
    ArcNo        int
    Title        string
    ChapterStart int
    ChapterEnd   int
    Summary      string
    Conflict     string
    TurningPoint string
    Climax       string
    CharacterChanges string
    OpenClues    string
    Status       string
    Version      int
}
```

默认每 5~10 章形成一个剧情单元，但允许用户调整范围。

### 4.4 `StoryBible` 故事圣经

```go
type StoryBible struct {
    ID              uint
    ProjectID       uint // unique
    Premise         string
    WorldRules      string
    MainPlot        string
    Subplots        string
    TimelineJSON    string
    RelationshipsJSON string
    ClueLedgerJSON  string
    LocationBibleJSON string
    PropBibleJSON   string
    AdaptationRules string
    Status          string // draft/approved/stale
    Version         int
}
```

故事圣经必须人工审核。章节重分析导致上游变化时标记 `stale`，但不直接覆盖用户已审核版本。

### 4.5 `CharacterPhase` 角色阶段状态

保留现有 `Character` 作为角色主档，新增：

```go
type CharacterPhase struct {
    ID            uint
    CharacterID   uint
    PhaseNo       int
    ChapterStart  int
    ChapterEnd    int
    Identity      string
    Appearance    string
    Wardrobe      string
    Motivation    string
    Relationships string
    PhysicalState string
    Knowledge     string
    Status        string // draft/approved
    Version       int
}
```

这样可以表达“入宫前/入宫后”“失忆前/恢复记忆后”等阶段变化。生成某集时按章节范围选择正确角色阶段。

### 4.6 `EpisodeAdaptation` 分集改编映射

```go
type EpisodeAdaptation struct {
    ID               uint
    ProjectID        uint
    EpisodeN         int
    Title            string
    ChapterStart     int
    ChapterEnd       int
    SourceChapterIDs string // JSON array，支持非连续章节
    TargetDuration   float64 // 默认 180
    TargetScenes     int     // 默认 25
    AdaptationGoal   string
    MustKeepEvents   string // JSON
    OptionalEvents   string // JSON
    OmittedEvents    string // JSON
    OpeningState     string
    EndingState      string
    Hook             string
    SourceDigest     string
    Status           string // draft/approved/scripted/stale
    Version          int
}
```

唯一索引：`(project_id, episode_n)`。

### 4.7 `NovelJob` 可恢复任务

```go
type NovelJob struct {
    ID         uint
    ProjectID  uint
    Type       string // parse/chapter_analysis/arc_merge/bible/episode_plan/continuity_review
    ScopeStart int
    ScopeEnd   int
    Status     string // pending/running/success/failed/cancelled
    Progress   float64
    Total      int
    Completed  int
    SkillID    *uint
    SkillVersion int
    Error      string
}
```

章节分析的每个章节是独立工作单元，失败章节单独重试。

## 5. 导入与章节切分

### 5.1 文件限制

首版支持：

- `.txt`
- `.md`
- 建议单文件上限 20 MB，可配置；
- 上传后计算 SHA-256；
- 去除 BOM、统一换行、过滤不可见控制字符；
- 原文永不自动改写。

### 5.2 章节识别

按优先级识别：

```text
第1章 / 第一章 / 第001章
第1卷 / 第一卷
Chapter 1
Markdown # / ## 标题
连续空行 + 短标题启发式
```

规则识别产生置信度：

- 高：匹配明确章节正则；
- 中：Markdown 标题；
- 低：启发式短标题。

低置信度必须进入“章节确认”页面，允许：

- 合并章节；
- 从光标位置拆分；
- 修改标题；
- 重新编号；
- 排除前言、目录、作者说明。

### 5.3 增量重导入

通过章节内容哈希比较：

- 未变章节保留分析结果；
- 修改章节标记 `stale` 并重分析；
- 后续剧情单元、故事圣经、分集映射逐级标记 `stale`；
- 不自动覆盖用户审核稿。

## 6. 分层分析策略

### 6.1 章节级分析

每章输入：

- 本章全文；
- 上一章 300~800 字摘要；
- 已知角色别名表；
- 当前世界规则简表。

输出严格 JSON，字数目标：原文的 3%~8%。

章节并发建议 2~4，避免文本 API 限流。相邻章节有依赖时采用滑动窗口：第 N 章分析读取 N-1 摘要，但不读取整本历史。

### 6.2 实体归一化

必须处理别名：

```text
萧炎 / 少爷 / 炎儿 / 他
```

流程：

1. LLM 输出候选实体和别名；
2. 使用规范名表做精确匹配；
3. 新别名以待确认状态加入；
4. 冲突时人工选择合并或新建；
5. 不允许模型直接删除已有角色。

### 6.3 剧情单元合并

每 5~10 章输入其结构化分析，不再输入全文。输出：

- 核心冲突；
- 因果事件链；
- 转折和高潮；
- 角色阶段变化；
- 新增/回收伏笔；
- 适合改编的集数建议；
- 可压缩、可删除的支线。

### 6.4 全书故事圣经

输入全部剧情单元摘要，分两步生成：

1. 并行生成时间线、角色弧、世界规则、伏笔、地点/道具；
2. 综合器检查冲突并生成最终故事圣经。

不能只用一次“全文总结”。最终圣经需要引用来源章节，例如事件 `E12` 保存 `chapter_ids`。

## 7. 改编策略

创建分集规划前由用户选择：

### 忠实程度

- **忠实改编**：保留事件因果和结局，仅压缩描写；
- **影视化改编**：允许合并场景、压缩支线；
- **爽剧强化**：允许提前冲突、强化反转与钩子；
- **自由改编**：保留核心人物和设定，其余可重构。

### 可配置项

- 改编章节范围；
- 目标集数；
- 每集目标时长，默认 180 秒；
- 每集目标镜头，默认 25；
- 必须保留角色/事件/名场面；
- 可删除支线；
- 是否合并角色；
- 结局是否允许修改；
- 内容尺度和平台规范。

这些设置写入 `StoryBible.AdaptationRules` 和项目 Skill 参数，不能仅存在前端表单。

## 8. 分集映射算法

### 8.1 事件权重

每个事件评分：

```text
importance       主线重要度 1~5
visual_value     视觉表现力 1~5
conflict_value   冲突强度 1~5
hook_value       结尾钩子价值 1~5
cost             改编时长成本
```

### 8.2 分配原则

1. 先按剧情单元确定集数配额；
2. 保持关键事件因果顺序；
3. 每集至少有一个冲突推进；
4. 除终集外，每集结尾有未解决问题；
5. 不在事件中间强行断集，除非刻意设计悬念；
6. 必保事件不可进入 `omitted_events`；
7. 相邻集重复引用同一章节时，必须明确不同片段或事件。

### 8.3 180 秒预算

默认分配：

```text
开场承接/钩子     10~15 秒
情境与目标建立     25~35 秒
冲突推进           70~90 秒
高潮/反转          35~45 秒
结尾钩子           10~15 秒
```

生成 20~30 个镜头，每镜 3~15 秒，总时长控制在目标的 ±10%。

### 8.4 审核界面

分集规划页按三栏展示：

```text
左：小说章节树
中：分集列表与时长预算
右：当前集引用事件、必保/省略内容和钩子
```

支持拖拽章节/事件到不同集，并实时检测：

- 章节遗漏；
- 关键事件重复或丢失；
- 因果顺序错误；
- 目标时长过载；
- 某集没有冲突或钩子。

## 9. 按集生成策略

### 9.1 上下文包

`EpisodeContextBuilder` 为每集构建有预算的上下文：

```text
A. 改编规则                     约 500 tokens
B. 世界规则与全局主线精简版       约 1,000 tokens
C. 当前角色阶段与关系             约 1,500 tokens
D. 上一集结尾状态/本集开场状态     约 800 tokens
E. 当前集来源章节摘要和事件         约 2,000 tokens
F. 必要原文片段                   约 4,000~12,000 tokens
G. 下一集目标/当前集钩子           约 500 tokens
```

超预算时优先保留：必保事件原文 > 当前集事件 > 角色状态 > 世界规则 > 描写性原文。

### 9.2 原文片段检索

首版不引入向量库：

1. 使用 `EpisodeAdaptation.SourceChapterIDs` 限定章节；
2. 按事件关键词、人物名、地点名查找相关段落；
3. 每段保留前后各一段上下文；
4. 去重后按原文顺序拼装；
5. 记录被引用的章节和字符偏移，支持追溯。

后续可增加 SQLite FTS5 BM25；只有规模和检索质量证明必要时再引入 embedding/向量数据库。

### 9.3 连续性状态

每集生成后提取 `EndingState`：

```json
{
  "characters": {"角色":{"location":"","physical":"","emotion":"","knowledge":[],"inventory":[]}},
  "relationships": [],
  "open_clues": [],
  "time": "",
  "location": ""
}
```

下一集生成前把上一集 EndingState 与当前 OpeningState 对比，不一致则阻止直接进入生产，要求修复或确认有意跳转。

### 9.4 双阶段生成

1. **改编剧本**：原文 → 约 3 分钟场景剧本，重点是剧情和对白；
2. **分镜拆解**：审核后的剧本 → 20~30 镜头 JSON。

不要让一次 LLM 同时承担长篇检索、改编、对白、分镜和图像提示词，否则输出更容易截断和产生非法 JSON。

## 10. Skill 设计

新增系统 Skill 阶段：

| Stage | Skill Code | 作用 |
|---|---|---|
| `novel_ingest` | `novel-chapter-parser` | 章节标题辅助识别与异常修复 |
| `chapter_analysis` | `novel-chapter-analysis` | 章节事件、人物、状态和伏笔抽取 |
| `arc_merge` | `novel-arc-merge` | 多章剧情单元合并 |
| `story_bible` | `novel-story-bible` | 世界观、时间线、角色弧和伏笔台账 |
| `adaptation_plan` | `novel-episode-mapping` | 章节/事件到分集映射 |
| `episode_adaptation` | `novel-episode-script` | 按来源原文生成单集剧本 |
| `continuity_review` | `novel-continuity-review` | 集间状态和因果一致性审核 |

安全边界保持不变：Skill 只提供提示词和输出规范，文件读取、数据库操作、分片和任务调度由 Go 服务完成。

每次调用记录：

- `skill_id/version`；
- 章节范围或集号；
- 输入内容哈希；
- 输出长度；
- 成功/失败；
- 耗时；
- 数据版本。

- 世界规则；
- 主线与支线；
- 角色弧；
- 关系图；
- 时间线；
- 伏笔台账；
- 地点和道具。

所有内容支持来源章节回跳和审核状态。

### 改编规划页

- 改编模式和目标集数；
- 章节/事件拖拽映射；
- 每集 180 秒和镜头预算；
- 必保、可选、省略事件；
- 覆盖率与连续性警告；
- 批量审核与逐集审核。

### 项目详情集成

项目来源类型增加：

```text
故事梗概
长篇小说
```

长篇项目的顶部步骤改为：

```text
原文 → 章节分析 → 故事圣经 → 改编规划 → 角色资产 → 单集剧本 → 分镜生产
```

故事圣经或当前集映射未审核时，不允许直接“一键全流程”。

## 13. 状态机与失败恢复

### 小说状态

```text
uploaded → parsing → chapters_ready → analyzing → analyzed
                                ↘ partial / failed
```

### 故事圣经

```text
missing → generating → draft → approved
                     ↘ failed
上游章节变化：approved → stale
```

### 单集映射

```text
draft → approved → scripted → produced
上游章节/圣经变化：approved/scripted → stale
```

规则：

- `partial` 允许查看已完成章节，但不能生成最终圣经；
- 单章失败不回滚已成功章节；
- 后端重启后扫描 `running` Job，根据子项结果恢复进度；
- 重试只处理失败或 stale 项；
- 生成结果用版本和 token 防止旧任务覆盖新审核稿。

## 14. 服务拆分建议

新增文件，避免继续膨胀 `project_service.go`：

```text
backend/internal/service/
  novel_import_service.go
  novel_chapter_parser.go
  novel_analysis_service.go
  story_bible_service.go
  adaptation_service.go
  episode_context.go
  continuity_service.go
  novel_handlers.go
```

服务依赖：

```text
NovelImportService    文件、编码、章节切分
NovelAnalysisService  调用 TextProvider + SkillService
StoryBibleService     分层合并与审核
AdaptationService     分集映射与单集上下文
ProjectService        继续负责剧本落库、分镜、图片、视频、合并
```

不要让 Skill 直接读取小说文件或访问数据库。

## 15. 性能与成本控制

- 章节分析并发默认 3，可在设置中调整；
- 按章节内容哈希缓存分析；
- 超长章节按自然段切为 8k~16k 字片段，先片段分析再章级合并；
- 所有合并阶段使用结构化摘要，不重复传全文；
- 记录输入字符数、输出字符数和调用次数；
- 可提供“快速分析/精细分析”档位；
- 用户修改一章时只失效依赖该章的剧情单元和分集。

## 16. 数据迁移与兼容

1. 现有项目默认 `source_type=idea`，行为不变。
2. `Project.Synopsis` 继续作为项目梗概，不存放长篇全文。
3. 旧 `plan.episodes` 缺少 `target_duration/target_scenes` 时默认 180/25。
4. 新 `EpisodeAdaptation` 可在首次打开旧项目时从现有 `plan.episodes` 延迟创建。
5. 新表全部通过 AutoMigrate 创建；已有数据不删除。
6. 删除项目时同步清理小说文件、章节、剧情单元、圣经、改编映射和 Job。

建议给 `Project` 新增：

```go
SourceType string // idea/novel
```

而不是用“是否存在 NovelSource”隐式推断，便于前端和流水线明确分支。

## 17. 测试计划

### 单元测试

- 中文数字、阿拉伯数字、卷章混合章节识别；
- 无章节标题的降级切分；
- BOM、CRLF、异常控制字符处理；
- 内容哈希和增量失效；
- 实体别名归一化；
- 分集事件覆盖率与因果顺序校验；
- 180 秒/25 镜头预算校验；
- 上下文预算截断优先级；
- EndingState/OpeningState 差异检测；
- 项目嵌套资源归属校验。

### 集成测试

使用不含版权风险的本地测试小说：

- 12 章、约 3 万字；
- 包含角色别名、跨章伏笔、时间跳跃、道具状态变化；
- 人为制造一个超长章和一个章节标题异常。

验收链路：

```text
上传 → 识别12章 → 修正章节 → 逐章分析
→ 生成2个剧情单元 → 故事圣经 → 6集映射
→ 生成第1/2集剧本 → 连续性审查
```

必须断言：

- 重试失败章不会重跑成功章；
- 分集映射覆盖全部必保事件；
- 每集镜头数 20~30，总时长 162~198 秒；
- 第2集能读取第1集结束状态；
- 每个关键结论能回溯章节来源；
- Skill 审计包含版本和范围。

### 性能验收

- 100 章章节列表分页加载稳定；
- 50 万字导入不把全文写入 API 响应；
- 重启后分析进度可恢复；
- 同一项目不能并发启动两个全书分析 Job。

## 18. 实施阶段

### 阶段 A：小说导入基础（3~5 天）

- 新增模型与迁移；
- TXT/Markdown 上传、清洗、章节识别；
- 章节确认与原文预览；
- Job 状态和进度；
- 单元测试。

**验收：** 50 万字 TXT 可导入、识别、人工修正章节，不调用 LLM。

### 阶段 B：分层理解（5~8 天）

- 章节分析 Skill；
- 并发、重试、缓存和断点恢复；
- 实体别名归一化；
- 剧情单元与故事圣经；
- 故事圣经审核 UI。

**验收：** 任一事件、角色变化和伏笔可回溯到来源章节。

### 阶段 C：分集改编规划（4~6 天）

- 改编策略配置；
- 事件评分与分集映射；
- 章节/事件拖拽调整；
- 180 秒预算与覆盖率校验；
- 映射审核。

**验收：** 生成的所有集都有来源章节、必保事件、目标时长和结尾钩子。

### 阶段 D：按集剧本与连续性（5~8 天）

- EpisodeContextBuilder；
- 原文段落检索；
- 双阶段“剧本 → 分镜”；
- 集间状态抽取与连续性审查；
- 接入现有角色/Krea2/H3 流程。

**验收：** 连续两集能保持人物状态、时间、地点、道具和伏笔一致。

### 阶段 E：完善（3~5 天）

- 增量重导入与 stale 传播；
- 批量操作和成本统计；
- DOCX/EPUB 可选支持；
- 端到端回归与用户文档。

总体预计：**20~32 个开发日**，建议 A→B→C→D 顺序推进，不同时铺开。

## 19. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 章节分析前后不一致 | 滑动摘要上下文 + 实体规范名表 + 单元合并复审 |
| 长篇伏笔被遗漏 | 独立 clue ledger，区分 opened/resolved，来源章节可追溯 |
| LLM JSON 不合法 | 严格 Schema、一次 JSON 修复、失败保留原始输出供重试 |
| 分集后半段空泛 | 先建立事件级映射，剧本不能脱离 SourceDigest 生成 |
| 角色状态漂移 | CharacterPhase + 每集 EndingState/OpeningState 对比 |
| 修改一章引发全书重算 | 内容哈希和依赖范围失效，仅重算受影响单元/集 |
| 成本不可控 | 分层摘要缓存、并发限制、调用统计、快速/精细档位 |
| UI 信息过载 | 小说、圣经、改编规划拆成独立页面，不堆在 ProjectDetail |
| 版权与隐私 | 本地保存原文、禁止日志输出原文、审计只存哈希和长度 |

## 20. 最终验收标准

长篇小说功能可认定完成需同时满足：

1. 能导入和人工修正至少 50 万字、100 章小说；
2. 分章分析可断点恢复，单章失败可单独重试；
3. 角色、事件、时间线、伏笔均可回溯原文章节；
4. 故事圣经和分集映射经过人工审核后才进入生产；
5. 每集默认约 180 秒、20~30 镜头，并记录来源章节和必保事件；
6. 单集生成不重复发送整本小说；
7. 连续性审查能检测人物地点、知识、物品和伤势跳变；
8. 上游原文变化能精确标记受影响结果为 stale；
9. Skill 版本和调用结果有审计记录；
10. 现有故事梗概项目保持原流程和数据兼容。

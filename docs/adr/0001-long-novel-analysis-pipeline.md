# ADR-0001：长篇小说分层分析与审核流水线

- 状态：Accepted
- 日期：2026-09-14

## 背景

阶段 A 已建立小说项目、章节导入和人工拆分/合并能力。阶段 B 需要对大量章节进行可重试的结构化分析，并将结果逐级归并为剧情单元和故事圣经。一次性把全文提交给模型无法保证上下文容量、追溯性、恢复能力和人工审核安全。

## 决策

1. 采用 `Chapter → ChapterAnalysis → StoryArc → StoryBible` 分层产物结构。
2. 章节分析结果保存来源章节版本和内容哈希；过期任务不得覆盖新版本。
3. 章节修改后，下游产物标记 `stale`，不自动覆盖已审核内容。
4. 批量分析使用持久化 `NovelJob` 记录范围、进度和失败，可从未完成章节继续。
5. 故事圣经使用 `draft/approved/stale` 审核门禁；未审核稿不能作为后续正式改编输入。
6. 新增 `chapter_analysis`、`arc_merge`、`story_bible` Skill 阶段。Skill 仅提供受控提示词与结构化输出约束；文件、数据库、网络和任务调度仍由 Go 服务掌控。
7. 角色别名作为候选映射单独保存，冲突映射必须人工确认，不能由模型直接合并角色主档。
8. 阶段 B 不实现分集映射、单集改编和连续性审查，它们留到阶段 C/D。
9. 保持 `source_type=outline` 的旧项目行为不变。

## 理由

- 分层摘要避免重复发送全书并降低上下文溢出风险。
- 来源版本与哈希提供可追溯和增量失效基础。
- 持久任务允许章节级失败重试和进程重启恢复。
- 人工审核门禁避免模型结果直接污染后续生产资产。
- 沿用现有 Skill 管理及审计能力，避免引入具备执行权限的新插件体系。

## 后果

### 正面

- 分析可按章节并行和局部重试。
- 事件、人物变化与伏笔可回溯原文章节。
- 后续分集改编可消费稳定、已审核的故事圣经。

### 代价

- 增加多张表、状态机和失效传播逻辑。
- UI 需要分别呈现章节分析、剧情单元与故事圣经。
- 必须维护来源版本、任务令牌和审核版本之间的一致性。

## 约束

- 不记录或输出用户原文到普通日志。
- API 中所有章节及产物查询必须同时校验 `project_id`。
- 同一项目同类批处理任务不得并发启动。
- 自动 JSON 修复仅修语法，不改写故事内容。
